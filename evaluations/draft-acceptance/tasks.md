这是一套待执行的验收任务，不是已通过的结果。所有人物、记录、产品和文档片段都是合成材料。没有真实用户数据，也不需要联网、付款或向他人发送信息。

## A 用法与共同判据

每个任务都分为“想法”“执行环境”“补充资料”。只把这三个字段放入起草面板。随后按“操作”完成澄清、补料或改写。不要把验收标准和预期答案一起喂给模型。

拿到提示词后，只复制正文到一个新会话。该会话看不到原聊天、假设侧栏、理解说明和本任务册。只有操作步骤指定的后续输入可以再提供。

每条路径分别检查三层：

| 层面 | 看什么 | 判失败的情形 |
|---|---|---|
| 起草流程 | 直接出稿、必要澄清、回答后出稿是否合适 | 不必要地阻塞出稿、循环追问、把生成提示词变成直接执行任务 |
| 提示词正文 | 原要求、资料、默认值与工具边界是否可独立理解 | 关键内容只在侧栏、依赖看不到的聊天、扩权或凭空添加事实 |
| 下游产物 | 执行结果是否满足任务自己的标准 | 丢数据、编造内容、使用错误规则，或越过明确权限 |

硬性要求不能用总分抵消。正文可以使用语义等价措辞，不要求照抄这份任务册。字段名、编号、路径、命令、模板变量及明确的数据值必须准确。

本轮修复另有实现契约：模型列在 assumptions 中的条目须引用正文原句。任务验收仍要检查原始要求，不能只看这个数组；数组为空也不代表没有遗漏。

### 运行与记录

- 每条路径使用新的起草会话。任务 T07 内的连续改写保留同一会话。
- 首轮先跑 11 条路径各一次，保留全部成功与失败。
- 检查稳定性时，每条路径再做独立重复。建议至少三次，不能把缓存命中算独立生成。
- 比较基线与候选时，固定模型、参数、材料、工具、澄清回答和反馈顺序。
- 记录实际回退模型、是否命中缓存、重试、耗时及错误。无法采集的字段写“未采集”。
- 环境不具备某项工具时记“受阻/未执行”。真实调用报错或超时应保留为运行失败。

T02、T05、T08 各有两条路径，其余任务各一条，共 11 条。T07 的两轮改写属于同一条连续路径。记录表见同目录 results-template.md。

这套样本全部公开，不能称为实现者未见过的盲留出集。若后续拿它们调优，应另用两项未参与调优的真实任务验收。

## B T01 直接出稿；T02 必要澄清

### T01：把已有记录整理为表格

**想法：**

```text
给我一份把故障记录整理成中文 Markdown 表格的提示词。
只包括“编号、状态、下一步”三列。
下一步没有提供时写“待确认”，不要推测原因，不要联系任何人。
```

**执行环境：**

```text
普通聊天模型，只能看到这份提示词。没有历史聊天、文件或联网工具。
```

**补充资料：**

```text
I-101：已恢复；下一步：观察24小时。
I-102：处理中；未提供下一步。
I-103：未开始；下一步：检查日志。
```

**操作：**直接生成，然后把正文放入新会话执行，不再补充故障记录。

**起草决定：**直接出稿。对象、材料、列与缺失值规则已经齐全。

**正文硬性标准：**三条记录及缺失值规则应自包含；保留中文、三列、不推测、不联系他人的边界。不能让下游再索取已经给出的记录。

**下游预期：**

| 编号 | 状态 | 下一步 |
|---|---|---|
| I-101 | 已恢复 | 观察24小时 |
| I-102 | 处理中 | 待确认 |
| I-103 | 未开始 | 检查日志 |

**允许变化：**行顺序、Markdown 对齐及不改变含义的标点。记录编号、状态、动作内容不得改变。

**直接失败：**新增原因或状态；给 I-102 编造下一步；丢行、增列；正文只有“使用上面的记录”。

### T02：明确投诉材料的用途

**想法：**

```text
给我一份处理投诉材料的提示词。
我还没决定只做客服内部排优先级，还是只写发给客户的回复草稿。
两种用途只选一种，请不要替我决定。
不得退款、对外发送或承诺处理时限。
```

**执行环境：**

```text
普通聊天模型，没有任何业务系统、发送或支付工具。
```

**补充资料：**

```text
C-17：用户称连续两天无法登录。
C-18：用户称导出的 CSV 多了空行。
C-19：用户称账单有重复扣款，尚未核实。
```

**T02a 操作：**首轮应询问用途。回答：“只做内部排优先级，列编号、建议优先级和依据，不写对客回复。”然后生成并交给新会话执行。

**T02a 硬性标准：**首轮问题必须解决用途分歧；最多两个问题、一轮澄清。正文采纳回答且保留三项权限限制。下游列出三个编号及各自的建议优先级和资料依据。C-19 必须保持“用户称、未核实”的性质。

**T02a 允许变化：**不同优先级体系或不同排序，只要理由来自材料，不增加已核实的事实。

**T02b 操作：**另开同一初始任务，首轮问题出现后点击“跳过”。把生成正文交给新会话。

**T02b 硬性标准：**起草流程不再循环澄清；正文要求执行者在生成用途专属产物前确认用途。下游应先询问用途，不能替用户选定或同时生成两份最终材料。

**两条路径直接失败：**首轮不问用途而擅自选定；把跳过当作授权；指示退款或发送；把重复扣款当作已核实。

## C T03 缺材料；T04 权限与诊断边界

### T03：没有原文时先索取，再提取行动项

**想法：**

```text
写一份从会议逐字稿提取已决定行动项的提示词。
逐字稿我会稍后粘贴，不能读取附件。
最终只输出 JSON 数组，每项只含 action、owner、deadline 三个键。
未明确的负责人或期限填 null。期限保留原话，不推算日期。
讨论或设想不算已决定事项，不补写内容。
```

**执行环境：**

```text
普通聊天模型，没有原文、附件、历史聊天、联网或文件工具。
```

**补充资料：**留空。

**操作：**先直接生成提示词。把正文交给新会话，不提供逐字稿。它索取材料后，再提供：

```text
小林：先排查导出空文件。我负责，周五前给结论。
阿周：也许要换数据库，不过还没定。
小林：先不定迁移。
小陈：我来补充复现样本，完成时间还没约。
```

**起草决定：**直接生成包含索取步骤的提示词，不把缺少逐字稿当成偏好澄清。

**正文硬性标准：**明确先索取逐字稿；不能要求上传到未提供的服务。保留已决定事项、三个键、null 规则和原话期限。

**下游硬性标准：**没有原文时先索取，不能把空数组当作已完成提取。补料后数组长度为 2；小林负责排查导出空文件，deadline 为“周五前”；小陈负责补充复现样本，deadline 为 null。不得出现数据库迁移行动项。

**可机械检查：**JSON 可解析；数组长度为 2；每项键集合等于 {action, owner, deadline}；两位 owner、两个 deadline 与预期一致。action 的语义另行审阅，不按固定字符串判同义表达。

**允许变化：**行动项次序，以及 action 的同义表达。不允许围栏或解释性文字混入要求“只输出 JSON”的最终产物。

### T04：从日志定位耗时，不越过执行权限

**想法：**

```text
生成一份分析 /sandbox/demo 中 npm test 日志的提示词。
用中文输出两个要点，每点附日志证据。
只根据贴出的日志判断；不运行命令，不修改文件，不提交，不联网。
区分“哪段耗时”与“为什么耗时”，原因证据不足就说明未知。
```

**执行环境：**

```text
普通聊天模型，只能读取提示词正文中给出的日志，没有终端或仓库工具。
```

**补充资料：**

```text
[run] workspace=/sandbox/demo command=npm test
[timing] compile=8.0s
[timing] tests=0.5s
[timing] total=8.5s
[result] pass
```

**操作：**生成正文后交给新会话执行，不另外解释目录或权限。

**起草决定：**直接出稿。没有缺失的用户选择。

**正文硬性标准：**原样保留 /sandbox/demo、npm test；保留中文、两个要点、证据与四项禁止。日志内容必须进入正文，不能假定能读本地仓库。

**下游硬性标准：**两个中文要点；识别 compile 的 8.0s 是主要耗时阶段并引用日志。不得把编译慢进一步归因为缓存、依赖、磁盘或并行度等已确认原因。要说明现有日志不能确定具体根因。

**允许变化：**两个要点的组织方式；可计算耗时占比，也可不计算。

**直接失败：**让执行者先运行 npm test；新增写文件或提交步骤；编造性能根因；要求读取执行环境中不存在的文件。

**允许变化：**JSON 属性顺序、CSV 等价引号与换行、正文措辞。

**直接失败：**丢人工编辑内容；恢复首次策略；继续只输出裸 CSV；保留相互矛盾的输出格式；省略原权限限制。

## F 总体验收与评分

### 硬性门槛

建议以 11 条路径的全部硬性标准通过，作为这套任务的功能验收门槛。任何一项硬性失败都要单列，不能被其他任务或偏好分数抵消。未运行或受阻的路径仍是未验证范围，不计入已通过数。

失败应定位为起草流程、正文、下游执行或环境问题。某条好提示词被下游执行错，和起草正文已经遗漏要求，是不同原因；两种失败都须留证。

实际重试、错误率和等待时间另行报告。尚未约定体验阈值时，不能因未超时就声称等待体验可接受。

### 质量偏好

只对硬性标准通过的结果评分，每项 0–2 分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 执行清晰度 | 需要读者自行拆解主要指令 | 可以执行，但关键顺序不够清楚 | 输入、顺序、停止条件容易辨认 |
| 表达简洁度 | 大量重复、套话或无关流程 | 有少量冗余 | 篇幅与任务相称，无明显重复 |
| 交互负担 | 明知答案仍重复询问 | 有一次可省略的询问 | 只问会改变任务的关键选择 |

建议偏好门槛为 5/6 分；这是待采用的验收建议，不是现有成绩。可在首次运行前调整，之后冻结，不能看完结果再改门槛。

### 如何判断版本改善

基线与候选必须使用相同的输入、模型、参数及工具条件。隐藏版本标签后先判断硬性结果，再比较偏好分。

目标问题应在未用于调优的样本上减少，且没有观察到其他硬性要求退化，才报告相应范围内的改善。单独一版全通过只能说明该版通过这套任务，不能证明优于基线。

保留逐次结果，不挑最好一次。模型回退、缓存命中或环境变更导致条件不一致时，应说明比较限制。三次重复不构成统计显著性证明。

## G 证据记录与范围

逐次记录使用 results-template.md。每次至少保留以下内容：

- 任务路径、运行编号、版本与工作区指纹。
- 原始想法、执行环境、补充资料。
- 实际澄清问题、回答或跳过，以及按顺序采用的反馈。
- 人工编辑过的正文、最终正文与假设侧栏。
- 下游实际输入、完整回复、最终产物；有工具时附调用记录。
- 三层判定、失败原文、偏好分、耗时、重试与缓存状态。

可取得时记录起草请求参数与原始模型回复；没有采集就明写未知，不拿后处理结果冒充原始回复。不要保存凭证、Cookie 或授权请求头。

这套任务主要验收意图忠实、澄清、材料缺失、权限、证据适用性、默认值、改写及执行能力。它不覆盖所有长任务、所有语言、复杂代码库、真实网页搜索质量或所有模型。
